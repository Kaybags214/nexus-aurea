Nexus Aurea — operating manual

Running it, day to day

Not how it was built. What to do when a document lands, what never to do with it, and what runs without you.

The whole job
  1. A document arrives. Decide: practice, or a real client? — see below, it matters more than anything else here.
  2. Audit it. Attach the photo, say “audit this.” Or run the script.
  3. Read the findings. Criticals first. Those block the shipment.
  4. Tell the sender what’s flagged. Send the corrected copy.

Most days none of that happens. You open the dashboard, nothing is red, you close it. That is the system working, not the system idle.

When a document arrives

Before anything else, answer one question. Getting this wrong is the only mistake here you cannot undo.

Practice

Invented parties. Apex Inc., ABC Flyers, your own filled forms, fixtures. Nobody real is named.

./scripts/audit-document.sh \
  path/to/doc.jpg

Report lands in the repo, gets committed and pushed. Shows on the dashboard next morning. This is your portfolio — it is meant to be seen.

Real client

A real company’s real shipment. Anything that arrived at kenya@nexusaureainc.com from someone who is not you.

./scripts/audit-document.sh --client \
  path/to/doc.jpg

Report goes to ~/nexus-aurea-client/. Nothing is committed. Git is never touched. The script refuses to run if that folder is inside the repo.

Why the report is as sensitive as the document. A findings report names the shipper, the consignee, the commodity, the AWB number and the declared value. It is a description of that client’s business. Committing the report discloses the same things as committing the document.

Reading what comes back

You seeIt meansYou do
🔴 CriticalThe shipment does not tender until this is fixedTell the sender. Every one.
🟡 MajorCorrectable before tenderInclude in what you send back
🟢 MinorFormatting, legibility, cleanupMention, don’t lead with it
Cannot verifyThe photo didn’t show itAsk for a reshoot. Not a finding.
Unverified in the sidecarA rule it could not confirm without your DGR copyCheck these yourself before sending.

The verdict line is the answer the sender wants. PASS, HOLD FOR CORRECTION, or REJECT — DO NOT TENDER. Lead with it.

Never, regardless of who asks

  • Never commit a real client’s document or report. Not redacted, not “just this once.” Redaction destroys the audit anyway — cross-document checking is party matching, so the names are the evidence.
  • Never send a PASS with an open Critical. Not if the sender pushes. The verdict is HOLD or REJECT.
  • Never sign or certify. You flag and correct. A qualified person signs before tender.
  • Never decide a product is fit for use after a temperature excursion. Only a QP or the MA holder releases product. You assemble the evidence; they decide.
  • Never assign an HS code. Flag it as absent or implausible and refer to a licensed broker.
  • Never state a regulatory limit from memory — yours or the system’s. Verify against the DGR, or record it as unverified.
  • Never send a real client document to a new AI service before the client has agreed to that processing.

Every day, every week

Daily — about a minute

Open the command centre. One question: is anything red?

  • Nothing red — close it. Done.
  • Criticals in Intake — that is your list, most recent at the top.
  • Next on the board — the specific things outstanding.

Weekly — fifteen minutes

The ARMS guide calls this keeping it alive, and it is the only maintenance the system needs.

  1. Read the new learnings.md entries. Each skill writes down what surprised it. This is where a skill’s second month beats its first.
  2. Fix one thing. A check in the wrong order, a state variation now known, a limit worth writing down with its edition stamped beside it.
  3. Delete a widget you stopped looking at. Same for a routine that never earns its run.
  4. Check retention. Client work older than 30 days after delivery gets deleted — document and report both.

The do-it-twice rule

Prompt the same task twice, make it a skill. That habit is what turned a generic assistant into yours, and it is the only rule that keeps compounding.

If you only remember three things

  1. Real client work never touches git. Use --client. The report is as sensitive as the document.
  2. Criticals block the shipment. Never a PASS with one open, however the sender pushes.
  3. Check the unverified list before you send. That is where the system tells you what it could not confirm — and it is the difference between a finding you can defend and one you cannot.
