# 06 — Concept Note: Autonomous Multifamily Operations Sandbox

**Status: DESIGN ONLY. Nothing here is built, and nothing should be built today.**
**Simulated events only. No real building, no real sensors, no real tenants, no real work orders.**

A future R&D direction: whether the pattern already proven in the DG document lanes — structured
review, computed status, human gate, audit trail — transfers to building operations.

---

## 1. The premise

The DG workflows do something specific and reusable: they take an ambiguous artifact, extract what
can be read, state plainly what cannot, compute a status from countable facts rather than asking a
model to self-assess, and stop at a human. The building-operations question is whether an ambiguous
*sensor event* is the same shape of problem as an ambiguous *document*.

Mostly it is. The sandbox exists to find where it isn't.

**The value being tested is not detection.** Sensors already detect. The value is everything after
detection: correlating an event with context, assessing severity consistently, drafting the
follow-up work, and leaving a defensible record of who decided what — the part that is currently a
person reading an alert at 2 a.m. and deciding on instinct.

---

## 2. The design constraint that shapes everything

**A human approval gate must never sit in the path of a life-safety alarm.**

This is the finding I would raise first against a naive build of this system, and it is worth
stating before the architecture rather than after. A smoke or CO alarm's own path to occupants and
to emergency services is a certified life-safety system. Nothing here may replace it, delay it,
suppress it, or sit between it and the people it protects.

So the gate applies to **follow-up work**, never to **alarm notification**:

```
smoke / CO event
   ├─→ the building's own alarm system does what it does        ← untouched, unmediated
   └─→ this sandbox: log · correlate · draft the follow-up      ← gated, and only this
```

Every other event class routes normally. This one splits, permanently, by design.

---

## 3. Simulated event classes

All six are synthetic, generated by a test harness. No real sensor, camera, or building system is
connected in this phase.

| Event | What it simulates | Severity driver |
|---|---|---|
| **Water leak / humidity anomaly** | Moisture sensor trip, sustained humidity above threshold | Escalates fast — water damage compounds hourly |
| **HVAC / temperature exception** | Unit out of range, sustained drift, short-cycling | Duration and outdoor conditions |
| **Smoke / CO alarm escalation** | Alarm state change | **Always highest. Never gated for notification** — §2 |
| **Door / access exception** | Door held open, propped, forced, unexpected hours | **Observation only** — §5 |
| **Maintenance photo → draft work order** | A photograph of a fault, image analysis, drafted task | Drafted, never dispatched |
| **Utility-usage anomaly** | Consumption spike or flat-line against baseline | Often the *earliest* signal of a leak or failed unit |

The last one is the interesting one. A utility anomaly is frequently the first evidence of a problem
another sensor will report hours later — a continuous-flow water reading before the moisture sensor
trips. Correlating across classes, rather than treating each alert alone, is a large part of what
the sandbox is for.

## 4. Architecture

```
[Simulated sensor / camera event]
        ↓
[n8n Webhook]              Header Auth · payload size and schema caps
        ↓
[Validation]               known device? known event type? plausible reading?
        │                  fails → REJECT_INTAKE, logged, no AI spend
        ↓
[AI / image analysis]      onError: stopWorkflow · alwaysOutputData: OFF
        │                  retry transport failures only, never content
        ↓
[Correlation]              recent events, same unit / stack / building
        ↓
[Severity decision]        COMPUTED from rules — never model-generated
        ↓
[Human Approval & Exception Gate]        review_type: building_maintenance_alert
        │                                (life-safety notification bypasses — §2)
        ↓
[Draft maintenance task]   DRAFT. Not assigned, not dispatched, not scheduled.
        ↓
[Audit trail]              event · analysis · severity · reviewer · decision · timestamps
```

Same hardening baseline as the DG lanes (`02-hardening-report.md` §1), same envelope
(`03-review-envelope-contract.md`, `review_type: building_maintenance_alert`), same gate
(`04-approval-gate/`). Nothing new is invented — the point is to test whether the existing pattern
carries.

**Reusing the envelope is not a cosmetic choice.** `missing_information` is where "the moisture
sensor on the floor below did not report" belongs, and it is exactly the field that keeps the system
from silently treating absent data as good news. The DG lanes already handle that well; the failure
mode is identical here.

**`environment: "sandbox"`** is stamped into every record and asserted before any write
(`02-hardening-report.md` F-P1). A sandbox that writes to a production audit trail is not a sandbox.

## 5. Explicitly out of scope

Not deferred. **Excluded.**

| Excluded | |
|---|---|
| Property purchase, acquisition, valuation | Not an investment tool |
| **Tenant surveillance** | No occupancy tracking, no behavioural inference, no identifying who is in frame. Cameras are for *equipment faults* only |
| Health care, elderly care, wellness monitoring | Not a care system, in any form |
| Medication handling | Out of scope entirely |
| **Autonomous access decisions** | Never locks, unlocks, grants, or revokes. Door events are **observed and reported**, never acted on |
| Humanoid robots / physical actuation | No physical action of any kind |
| Autonomous dispatch | Work orders are **drafted**; a person assigns them |
| Emergency-services contact | The alarm system does that. This does not |

Two of these deserve their reasoning stated, because they are the ones a build would drift into by
accident:

**Tenant surveillance.** A camera pointed at a mechanical room to catch a leak and a camera pointed
at a corridor to watch residents are the same hardware and completely different systems. The
boundary is the *analysis target*: equipment and building fabric, never people. An image pipeline
that identifies a person has left scope, and should be treated as a defect.

**Autonomous access.** A door-held-open event is a legitimate maintenance and security signal. Acting
on it is not — an automated lock decision can trap someone inside or lock a resident out, and neither
failure is recoverable by a workflow. Observe and report.

---

## 6. What the sandbox is actually testing

Four questions, each with a real chance of a negative answer:

1. **Does computed severity beat human triage for consistency?** The DG lanes compute status from
   countable facts (`02` F-6). Whether the same works when the input is a sensor reading rather than
   a document field is an open question, and the answer might be no.
2. **Does correlation across event classes surface problems earlier than single alerts?** The
   utility-anomaly-precedes-leak hypothesis in §3.
3. **Is a drafted work order actually useful, or does correcting a bad draft cost more than writing
   a good one?** This is the one most likely to fail. A draft that is 80% right can be slower to fix
   than a blank form.
4. **What is the false-positive rate at each severity, and does the gate hold up under it?** A gate
   a reviewer clicks through fifty times a day is not a control — it is a formality, and a formality
   in the audit trail is worse than an honest gap because it manufactures confidence. If the volume
   is high, the design is wrong.

Question 4 is the one that decides whether this is worth building at all.

---

## 7. Phasing

| Phase | Content | Gate to the next phase |
|---|---|---|
| **0 — today** | This note. Nothing built. | Decide it is worth prototyping |
| **1** | Synthetic event generator + envelope + severity rules. No AI, no gate. | Severity rules produce stable, defensible results on synthetic data |
| **2** | Add image analysis on stock photographs of equipment faults. | Analysis adds something the rules did not already have |
| **3** | Wire the approval gate. Measure question 4. | False-positive volume is low enough that the gate stays a real control |
| **4** | Draft work orders. Measure question 3. | Drafts save time rather than cost it |
| **Not planned** | Real sensors, real building, real tenants. | A separate decision, with legal and insurance review, not a continuation of this |

Phase 4 → real deployment is deliberately **not** drawn as an arrow. It is a different decision with
different stakeholders, and treating it as the natural next step is how sandboxes leak into
production.

---

## 8. Relationship to the compliance lanes

Shared: hardening baseline, review envelope, approval gate, audit trail, redaction discipline.

Not shared: **nothing from the DG lanes may depend on this.** A building-operations experiment must
never become a dependency of a dangerous-goods compliance path. Separate n8n project, separate
webhook paths, separate credentials, separate audit store. If the sandbox is deleted tomorrow, the
DG workflows must be entirely unaffected.

---

## 9. Standing constraints

- Simulated events only. No real building system integration in any phase described here.
- No tenant data of any kind — not names, not unit occupancy, not schedules, not images of people.
- No autonomous physical action, no access control, no emergency dispatch.
- Every output is a draft. Every action is taken by a person.
- No Alacran data, systems, workflows, credentials, or integrations.
